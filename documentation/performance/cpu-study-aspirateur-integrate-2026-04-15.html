Conclusion exécutive

Le CPU du pipeline n’est pas consommé par une seule fonction isolée. Il part surtout dans les multiplicateurs: trop de collectes larges, trop de transformations répétées, trop de sérialisations JSON, trop de normalisations de tableaux, et trop de petits payloads qui repassent dans Integrate::evaluate().

Le levier principal n’est donc pas le micro-tuning ligne par ligne. Le vrai levier est de faire moins de travail redondant, à sortie identique. Cette étude sépare trois vagues de travail pour garder un risque maîtrisé.

Vagues proposées

  • Wave 1: optimisations CPU transparentes dans `Aspirateur`, sans changer fréquence ni données collectées.
  • Wave 2: réduction du CPU pur PHP dans `Integrate` sur les parcours, typages, échappements et caches metadata.
  • Wave 3: optimisation du pipeline complet via batching et réduction de la fragmentation des payloads.

Périmètre et contrainte

La demande explicite a été respectée pour la branche courante:

  • Conservé même contenu collecté
  • Conservé même fréquence de collecte
  • Conservé même format fonctionnel des exports
  • Ciblé uniquement le CPU perdu dans du travail redondant ou mort

Plan de réduction CPU

Wave 1 - transparent

  • supprimer le travail mort
  • cacher les metadata relues dans le même cycle
  • éviter les rescans inutiles

Wave 2 - Integrate

  • éviter les `array_change_key_case()` multiples
  • cacher `ts_file` et `ts_variable`
  • réduire `getTypeOfData()` / `isJson()` sur les chemins chauds
  • réduire les concaténations et échappements répétés

Wave 3 - pipeline

  • réduire le nombre de `exportData()` par run serveur
  • réduire la fragmentation des payloads
  • envoyer des blocs plus cohérents à `Integrate`

Règles à respecter

  • ne pas changer la donnée métier sans décision explicite
  • ne pas changer la fréquence de collecte sur les branches transparentes
  • mesurer avant / après avec micro-bench et test ciblé
  • séparer les gains sûrs des gains structurels plus risqués
